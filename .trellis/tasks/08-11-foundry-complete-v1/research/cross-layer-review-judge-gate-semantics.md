## Diagnosis / Observe evidence

Grounded in exact offline reproduction (`/tmp/judge-repro` rendered candidate
runtime, `/tmp/verifier2-exact.py`), re-verified against source:

- **Reset defaults are framework-deterministic but undisclosed.** The rendered
  candidate runtime is generated by framework code
  (`candidate.py _DESIGN_RUNTIME_BODY`, lines ~191-340) whose `reset` calls
  `_init()` -> `_default(category, values)` BEFORE applying initial_config.
  That `_default` (candidate.py 191-203) is the true reset source:
  boolean False, integer 0, number 0.0, list [], enum values[0] else "", timestamp
  "1970-01-01T00:00:00Z", else "" (NO identifier branch -> identifier -> "").
  With world_rules.initial_rules empty, nothing disclosed these values to the
  task_requirement model, and no compile check verified the guesses.
- **Transition degeneracy / self-reference.** tool_semantics compile
  (`design.py _direct_tools`, ~1925-2170) validates shape + effect category but
  not that two transitions share identical whens, nor that a when predicates a
  field no transition effect ever sets.
- **Verifier-case guard violation.** `candidate.py _private_verifier_cases`
  (~1601-1622) builds case arguments from raw `_field_value` category defaults
  and passes them unguarded as `varied_arguments`; `_run_recipe`
  (runtime.py 795-800) uses raw varied arguments without `_guard_arguments`,
  so the composition checker's precondition_guards requirement
  (runtime.py ~832-840) can never hold -> `local_tool_semantics_mismatch`.
- **Judge evidence detail dropped.** `judge()` (runtime.py 1038-1169) returns
  outcomes with gate_id/status/code/binding only; `_judge_node`
  (candidate.py ~1705-1714) persists exactly those + candidate_digest, dropping
  `detail` that `_run_recipe`/`_task_outcome` path already computes in some
  branches.

## Drift-risk / co-ordination flags for implementation (non-blocking)

1. **Parity target must be the scaffold `_default`, not the other two copies.**
   There are ALREADY three divergent reset/argument-default implementations:
   `candidate._DESIGN_RUNTIME_BODY._default` (identifier->"", text->""),
   `candidate._field_value` (identifier->"public-id", text->""),
   `runtime._value` (identifier->"public-id", text->"sample-text"). The plan's
   enumerated reset list correctly mirrors the scaffold `_default`; the parity
   test MUST assert against `_DESIGN_RUNTIME_BODY` literal (the actual reset
   source), never `_value`/'sample-text'. The plan's "shared helper would
   drift" concern is vindicated: the three copies already disagree, so the
   parity test is the right guard.
2. **`_binding_fields_for_llm` is a 4-consumer shared helper.** Called at
   design.py 2094 (tool_semantics), 2203 (world architecture), 2676
   (task_requirement), AND candidate.py 1079 (builder). Adding `reset_value`
   unconditionally would leak a reset column into tool_semantics /
   world-architecture / builder projections. reset_value disclosure must be
   scoped to the task_requirement projection only (parameterized or a separate
   projection), and enum `values` (needed for "enum values[0]") must be
   sourced from the tool surface at compile time, not from the LLM field rows.
3. The simulation correction's interpolated text (field + simulated post_state
   outcome + the fixed guidance) can approach 280 chars once values are
   inlined; use the bounded-render idiom (trim + "...") so the CorrectionPacket
   can never fail its own `__post_init__`.
