# Direct LLM And Deep Research Node Execution

## Goal

Replace the current hardcoded non-IMPLEMENT node factories with directly executable LLM, research, and tool-discovery node execution. The task is explicitly not about preserving deterministic generation as a fallback and not about maintaining old tests that encode the hardcoded behavior.

After this task, the request-driven pipeline success path should depend on real configured node executors:

- S1 performs source discovery through a research/search agent path.
- S2/S3/S4/S5/S7 generate structured artifact fields through LLM/agent execution.
- S8 includes LLM feasibility judgment as advisory input while framework policy keeps final authority.
- static artifact validation, gates, and framework release checks still run after generation.

If required LLM/research configuration is missing in the live path, the run should fail or return `needs_human`; it must not silently fall back to old deterministic artifact generation.

## Background

The source-of-truth architecture says agents should participate in explicit nodes for search, extraction, synthesis, judgment, code generation, review, or repair, while the framework owns workflow, artifacts, gates, trace, budgets, repair decisions, and release decisions.

Current implementation has the pipeline shape but not the intended execution behavior:

- `agent_world/pipeline.py` defines `PipelineNode.factory`.
- `_run_artifact_node()` calls `fields = node.factory(context)` for non-IMPLEMENT nodes.
- many stages are marked `allowed_agent_backend=True`, but that flag does not cause an agent invocation.
- `IMPLEMENT` is the only major real agent-backed path today.
- upstream artifacts are mostly generated by deterministic Python functions in `agent_world/request_driven.py`.

## Problem

The current deterministic factories make the pipeline look functional while bypassing the intended work:

- S1 does not perform real source discovery.
- S2 does not perform LLM extraction from evidence.
- S3/S4 do not perform LLM synthesis or tool-surface discovery.
- S5/S7 do not perform LLM task or verifier planning.
- S8 does not contain meaningful LLM feasibility judgment.

Because these artifacts are hardcoded, later semantic verification and feedback loops have little value. The project first needs real LLM/research execution in the node chain.

## Requirements

### R1. Remove Deterministic Generation From The Success Path

Non-IMPLEMENT node success must not depend on the existing hardcoded `request_driven.py` generation functions.

The implementation may keep tiny deterministic helpers only when they are not generating semantic artifacts, for example:

- JSON/schema normalization;
- ID or hash helpers;
- framework policy checks;
- test-only stubs that never produce accepted semantic artifacts.

But old deterministic artifact generation must be removed from the normal request-driven success path. Existing tests that require the hardcoded output should be updated or deleted.

### R2. Direct Live Node Execution

Implement direct agent-backed execution for non-IMPLEMENT nodes. This must not stop at defining interfaces.

Required live node paths:

- S1 `SourceEvidenceIndex`: research/search agent using local sources plus configured search/tool provider.
- S2 `KnowledgePack`: structured LLM extraction.
- S3 `EnvironmentSpec`: structured LLM synthesis.
- S4 `LogicalToolGraph`: LLM/tool-discovery-assisted graph generation.
- S5 `TaskSet`: structured LLM task generation.
- S7 `VerifierPlan`: structured LLM verifier planning.
- S8 `FeasibilityReport`: deterministic checks plus LLM feasibility review, with framework-owned final status.

### R3. Use Existing AgentBackend Boundary

Reuse the existing `AgentBackend` and OpenAI-compatible backend path where possible. Do not scatter direct SDK/API calls inside pipeline core.

Pipeline core should build `AgentRequest`, invoke an executor/backend, receive structured fields or structured failure, and then continue with artifact validation and gates.

### R4. Implement A Lightweight Research Agent

S1 should not be a thin search wrapper. It should be a small research workflow:

1. build a query plan from `DomainPlan`, `NeedSpec`, raw request, and provided source paths;
2. scan local sources;
3. run a configured external search/provider path;
4. read or summarize candidate source snippets/pages where available;
5. use LLM judgment to select useful evidence;
6. output valid `SourceEvidenceIndex` fields.

Required provider paths:

- local source provider;
- SearXNG-compatible HTTP search provider when `AGENT_WORLD_SEARXNG_URL` is configured;
- process-based search provider when `AGENT_WORLD_RESEARCH_CMD` is configured.

### R5. Structured LLM Artifact Generation

For S2/S3/S4/S5/S7/S8 advisory review, prompts must request JSON fields for the target artifact, not prose and not full artifact wrappers.

The framework should:

- provide upstream artifacts in the prompt;
- provide stage-specific skills when configured;
- require a JSON object response;
- parse JSON with bounded repair if necessary;
- wrap fields with `make_artifact()`;
- fail with structured diagnostics when output is invalid.

### R6. Support Stage-Specific Agent Skills

Some agents need more than a prompt. The node execution layer should support stage-specific skill packs: durable instruction bundles that define tools, workflow rules, output contracts, examples, and safety constraints for a node.

Required skill packs:

- `research-source-discovery`: for S1 research/search/source evidence generation.
- `knowledge-extraction`: for S2 source-grounded extraction.
- `tool-surface-discovery`: for S4 MCP/CLI/API/SDK/tool discovery and graph planning.
- `task-generation`: for S5 task set generation.
- `verifier-planning`: for S7 verifier plan generation.
- `feasibility-review`: for S8 advisory feasibility judgment.

Skills should be loaded as input context to the relevant agent invocation and referenced in invocation records. Skill assignment must be configurable: a stage may load more than one skill, and different executor/backend profiles may use different skill sets for the same stage. Skills are not release authority; artifact validation and gates still decide acceptance.

### R7. Preserve Checks, Not Old Generation

Static artifact validation, gates, review records, package identity checks, and runtime verification remain required.

This task removes deterministic generation from the success path, not deterministic validation.

### R8. Record Invocations And Evidence

Every LLM/research node must produce records usable by later verification and repair:

- backend/provider kind;
- stage;
- node purpose;
- skill refs used by the invocation;
- executor/backend profile that selected those skill refs;
- input artifact ids;
- output artifact id when accepted;
- evidence refs;
- trace refs;
- failure class and recovery suggestion.

### R9. Keep Framework Authority

LLM/research nodes may generate, search, judge, and recommend, but they cannot bypass:

- artifact validation;
- stage gates;
- framework-owned runtime verification;
- release/package identity checks.

S8 can include LLM feasibility judgment, but final pass/fail/needs_human remains framework-owned.

## Non-Goals

- Do not implement full cross-stage repair loop in this task.
- Do not preserve old deterministic request-driven generation behavior as a fallback.
- Do not keep tests solely to protect old hardcoded artifact outputs.
- Do not let agent output decide release acceptance.
- Do not vendor large open-source research projects into `agent_world/`.
- Do not restructure envpkg packaging unless invocation metadata requires small additions.

## Acceptance Criteria

- [ ] Non-IMPLEMENT node execution no longer uses hardcoded `PipelineNode.factory` / `request_driven.py` artifact generation as the success path.
- [ ] S1 runs through a research/search agent path and emits `SourceEvidenceIndex` from discovered evidence.
- [ ] S2/S3/S4/S5/S7 run through structured LLM/agent generation.
- [ ] S8 includes LLM feasibility review and deterministic framework final decision.
- [ ] Missing live LLM/research configuration fails clearly or returns `needs_human`; it does not silently use deterministic generation.
- [ ] Existing tests that encode deterministic generated artifact content are updated or removed.
- [ ] Tests do not create accepted semantic artifacts through mock LLM/research success paths; they may stub transport-level providers or invalid agent output only for failure diagnostics.
- [ ] Search/research results are reflected in `SourceEvidenceIndex.sources` and evidence refs.
- [ ] Stage-specific skill packs are loaded for configured research/LLM nodes and referenced in invocation records.
- [ ] Invalid LLM JSON or invalid artifact fields fail with structured diagnostics.
- [ ] IMPLEMENT behavior remains compatible with existing code-agent candidate checks unless a direct replacement is implemented.
- [ ] Documentation explains required env vars/config for live LLM/research execution.

## Implementation Bias

Prefer direct working integration over framework scaffolding. Add only enough execution plumbing to keep pipeline core clean and to avoid scattering LLM/search calls across stages.
