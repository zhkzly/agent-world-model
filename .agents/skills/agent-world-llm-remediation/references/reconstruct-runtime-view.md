# Reconstruct the Runtime Recipient View

Read the actual node-facing materials, not a similarly named repository
template. For each item, record its coordinate and effective path, identifier,
or projection:

- rendered Prompt and input projection;
- mounted Runtime Skill bundle for a Codex Agent, or proof that a Direct route
  has no Skill/tool/Hook/profile instruction surface;
- granted tools/workspace and frozen input view for a Codex Agent;
- resolved model, route, response mode, budget, and timeout;
- output, validation result, safe observe scene, and attempt authority.

Describe what the recipient could reasonably infer, what it may have
misunderstood, and what was not visible at that time. Do not use later
Integration/Judge evidence as if it was already available to the first attempt;
only an explicitly attached safe correction brief can add it to a new turn.

## Zero Provider event is a mechanical branch

When the safe terminal is sdk_session_open with zero Provider events, Prompt
and Runtime Skill did not reach the model. Keep their lenses unknown. Inspect
the app-server launch, SDK arguments, generated config, profile materialization,
adapter, and safe diagnostics first.

The profile must not create an alternate instruction channel: worker payloads
omit base/developer instruction fields rather than sending empty or generic
replacement text. If the normal phase cannot identify startup cause, use an
opt-in bounded redacted local diagnostic sidecar. Never place raw provider
text, credential, endpoint, private session state, or opaque startup material
in normal scene, Artifact, graph/Observe feedback, or runtime correction.
